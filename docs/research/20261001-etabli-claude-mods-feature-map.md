# Etabli : cartographie des fonctionnalités qui peuvent bénéficier des Claude mods

Date : 2026-10-01. Révision analysée : `fd4bf728f297eae867e5115ab10e3269fb037992`. Question : quelles fonctionnalités déjà présentes dans Etabli peuvent profiter des mods, avec quel bénéfice concret et quelles limites ?

## Conclusion

Le bénéfice dépasse largement un dashboard : les mods peuvent rendre visibles les preuves du workflow, proposer des commandes locales immédiates, expliquer les refus, suivre agents et budgets, améliorer la QA et présenter les outils ou skills adaptés. Cependant, la majorité des règles utiles existe déjà dans Etabli. Le bon investissement est une couche Claude mince, qui projette ces autorités et appelle leurs helpers déterministes. Réimplémenter le workflow, le retrieval ou les revues dans un mod créerait surtout des divergences.

**verified** : cette étude recense **70 comportements** dans les sources actuelles, couvrant les neuf entrées Pi, les hooks Claude, les contrats, les scripts, les skills et les routines maintenus. **inference** : les propositions de mods sont des possibilités d'intégration, pas des fonctionnalités livrées. **blocked** : le dernier essai du test kit avec Claude local 2.1.287 a été refusé avant les tests par le rollout distant. **not verified** : aucun mod Etabli, runtime installé, planning launchd ou flux fournisseur n'a été exercé dans cette étude.

Le premier résultat utile serait `/etabli`, une commande immédiate en lecture seule alimentée par **`scripts/session-handoff`**, accompagnée d'une vue des checks et de leur provenance. Ensuite viennent la consommation native et les preuves de revue. Les guards, la redaction et la compaction exigent des preuves de parité supplémentaires avant toute substitution.

## Comment lire la matrice

Chaque comportement existant est **verified** au niveau source ; chaque bénéfice proposé est **inference**. **P0** : premier résultat utile et borné en lecture seule. **P1** : amélioration après la première preuve runtime. **P2** : conditionnelle à un besoin confirmé. **P3** : valeur faible ou absence de port conseillé.

Dispositions : **UI** = projection sans décision nouvelle ; **observateur** = suit les événements/résultats ; **commande mince** = invoque explicitement une autorité existante ; **guard shadow** = compare la décision sans devenir le contrôle autoritaire ; **pas de port** = garder le système actuel. Les événements/API de la matrice sont documentés dans la recherche précédente. Ils ne constituent pas des signatures garanties identiques entre versions.

Une preuve commune à toutes les lignes est nécessaire : mod chargé dans le runtime réel, types de la version installée, comportement exercé dans les surfaces supportées, résultat associé à la bonne session et au bon worktree. La dernière colonne ajoute les preuves spécifiques ; elle ne prétend pas qu'elles existent déjà.

## Les contraintes qui changent réellement la conception

### Une couche mince doit traverser un processus Node

Le core workflow importe `node:fs`, `node:child_process`, `node:path` et des helpers scripts. Le chargeur mod n'accepte que des imports relatifs internes au plugin et `claude-code`; il interdit les imports Node et ne laisse pas transmettre `$` à une fonction importée. Un mod ne peut donc pas simplement importer `workflow-router-core.mjs` ou les extensions Pi.

L'intégration minimale est un appel `$.process.run` avec argv vers un helper Node canonique, en passant explicitement cwd/worktree et données minimales. Il faut traiter `exitCode` : un exit non nul est un résultat résolu, tandis qu'un timeout ou défaut de démarrage peut rejeter. Pour un guard autoritaire, une erreur avant `next` est normalement fail-open : il faut une réponse deny explicite dans le délai et prouver l'ordre des plugins. Conserver les hooks actuels pendant cette comparaison. Sources : recherche précédente ; `workflow/runtime/workflow-router-core.mjs:1` ; [guide des événements](https://code.claude.com/docs/en/plugins/mods/events).

Isoler plus tard un cœur pur avec dépendances explicites est une possibilité, seulement si la mesure justifie le coût de maintenance. Copier la policy dans le mod pour économiser un subprocess serait une divergence. Le dépôt public Claude comporte une licence « all rights reserved », pas une licence permissive implicite permettant de recommander le vendoring de ses mods.

### L'interface dépend du mode d'exécution

**documented** : les panneaux et bandes se dessinent dans le terminal interactif et l'onglet Code de Claude Desktop. Les hooks peuvent fonctionner dans `claude -p`, l'Agent SDK et le chat VS Code, mais leur interface n'y est pas dessinée. Les runners de revue doivent donc conserver leurs rapports et receipts ; un panneau dans la session parente peut en présenter les résultats. En Remote Control mobile, l'interface du mod reste dans le terminal de la machine. La disponibilité dans le cloud dépend aussi du chargement effectif du plugin. [Matrice officielle des modes](https://code.claude.com/docs/en/plugins/mods/overview#where-mods-run).

Les éléments UI fournis ne constituent pas un navigateur avec DOM. Les dossiers Playwright, pages HTML et exports restent des artefacts à ouvrir dans leurs outils. Le dialogue de permission n'est pas un site de rendu modifiable ; un écran Etabli ne peut pas remplacer la permission native. Les panneaux ouverts spontanément ont aussi des conditions de largeur, contrairement à une ouverture demandée par l'utilisateur. [Interface officielle](https://code.claude.com/docs/en/plugins/mods/interface).

### Les preuves doivent précéder les couleurs et les effets

Un résultat vert exige identité de révision, exécution terminale, exit code et portée. Les statuts de transport, review completion, tokens et livraison restent distincts. Deux pièges source particulièrement concrets : `claude/scopes/work/scripts/sessions-report-prompt.md:9` et plusieurs prompts routines terminent leur marker même après des publications échouées ; `claude/scopes/work/scripts/pr-autoreview/run.sh:96` peut terminer exit0 après échec et seen marque une exécution exit0, pas un reçu Slack. Le futur panneau doit montrer cette incertitude au lieu d'affirmer « livré ».

`$.fs.write` ne fournit pas de remplacement atomique et `$.store.get/set` pas de CAS. Le store est partagé sur la machine ; il faut clés de worktree/session et aucune autorité du ledger transférée vers le store. Les leases eux-mêmes nécessitent une projection sans token avant passage dans stdout, UI ou stockage. Les accès du mod aux fichiers/processus/réseau ne sont pas confinés par les refus d'outils destinés au modèle : limiter les capacités du mod et leur admission est un travail distinct.

`$.state` survit au rechargement du module, mais repart à ses valeurs par défaut lors de `/clear`, `/resume` et `/branch`. Le panneau doit alors relire ses sources, via les événements classiques correspondants, et afficher le worktree, la révision et la date de sa dernière lecture. Le changement de HEAD ou de fichiers depuis un autre processus peut également rendre une projection périmée. La persistance et les preuves de clôture ne doivent pas dépendre de `session.end`, dont le budget total est de 1,5 seconde. [Cycle de vie de l'état](https://code.claude.com/docs/en/plugins/mods/interface#keep-state), [délais des hooks](https://code.claude.com/docs/en/plugins/mods/reference).

Un mod utilisateur peut modifier certains refus d'un hook `PreToolUse` non managé ; les hooks managés ont une priorité différente. La comparaison d'un guard doit donc couvrir sa composition avec les autres plugins, ainsi que les appels directs `$` aux fichiers et aux processus. Reproduire seulement son message de refus ne prouve pas son autorité. [Politique d'administration des mods](https://code.claude.com/docs/en/plugins/mods/admin).

### Raisonnement, retrieval et orchestration restent dans leurs systèmes

Les commandes review, plan-loop, implement, ship, bug-check, pr-qa et sec-pr contiennent des procédures de raisonnement et des checkpoints. Un mod peut présenter données et actions ; il ne remplace pas ces skills par une fonction automatique. La récupération durable reste dans obvault/brain, le workflow dans le plan/ledger, les agents dans le runtime natif. `model.fork` hérite de la conversation et du modèle : ce n'est pas un reviewer indépendant. `session.send` ne constitue pas un protocole d'achèvement/exactly-once. Les timers ne survivent pas à une CLI arrêtée.

Les boutons de lancement de check, mutation, publication ou agents sont des actions séparées des vues en lecture seule. Conserver leur autorité actuelle et leur provenance ; ne pas inventer une instruction humaine via `prompt.submit`/`asUser`. Pour les routines, une autorité inscrite dans leur propre invocation n'autorise pas un nouvel automatisme de publication depuis toute session Etabli.

## Séquence proposée, sans mise en œuvre dans cette recherche

1. **Débloquer la preuve runtime** : attendre une session où le rollout accepte réellement les mods, générer les types locaux, vérifier rendu et événement dans une session jetable. La [documentation troubleshoot](https://code.claude.com/docs/en/plugins/mods/troubleshoot) indique que le refus « turned off in this process » correspond à une désactivation distante et n'a pas de réglage local pour la contourner. Ne pas confondre version suffisante et fonctionnalité active.
2. **Commande immédiate `/etabli`** : reprendre la projection JSON de session-handoff, ajouter liens et expliquer absence/ambiguïté de ledger. Périmètre initial : lecture seule, un worktree explicite, aucun appel modèle ni réseau. Avec `immediate:true`, un rendu human-only et retour `{}` peuvent éviter un nouveau tour modèle ; retourner `text` le rend lisible au modèle et peut augmenter le contexte suivant. Aucun gain global de tokens n'est établi.
3. **Panneau de preuves** : checks et pack de revue, hashes/SHA, erreurs/annulations/unknowns. Rendu TUI puis Desktop selon APIs réellement disponibles ; benchmark d'utilité et de latence du helper.
4. **HUD et catalogue** : mesurer usage/context/cache, puis skills/scopes et rôles d'agents. Comparer avec statusline actuelle ; ne pas promettre baisse de coût sans baseline et répétitions.
5. **Guards en shadow** : READY, freeze, commit, read-only ; mêmes fixtures et cas adverses, conflit d'ordre, helper down, timeout, exit non nul, multi-worktrees. Passage autoritaire seulement après parité démontrée et choix d'activation concret.
6. **Expériences spécialisées** : redaction complète des canaux, reprise/compaction, QA dossiers, diagnostics routines. Les écritures, publications, nouvelles délégations et choix fournisseur gardent les checkpoints existants.

Cette séquence couvre d'abord les fonctions déjà déterministes et bien projetables ; elle évite de faire dépendre les protections actuelles d'un runtime mod encore non démontré localement.

# Research result

**Status: Partial**

Held-out and sealed task populations, outcome-only grading (not “run finished”), pass@1/pass^k chosen to match product consistency, mechanical answer-quality floors, and capability matrices with expiry plus proof_command re-proof are the patterns that raise coding-agent reliability rather than docs or suite theater. Literature and production harness writeups converge on contamination-resistant partitions, independent final-state graders, and adversarial claim checks; score gains on open static corpora increasingly track training exposure and harness leakage. Multi-agent hop count is not a quality metric without independent outcome verification. For a dual-runtime harness that already has router evals, check-freeze guards, and optional vNext suites, transfer the patterns below—each with mechanism, measurable signal, and non-applicability bounds.

### Sealed and held-out task populations
Continuously date-tagged contest problems score newer models only on post-cutoff items; large drops on pre-cutoff windows (e.g. after Aug/Sep 2023 or Nov 2023 on LeetCode) show training leakage that static suites miss.[S1] Agent benchmarks often lack adequate holdouts, which enables shortcuts and overfitting so leaderboard accuracy fails to transfer; holdouts should match the claimed generality (in-distribution, OOD, held-out tasks, or held-out domains).[S2] Production-style coding testbeds partition public vs non-public sets—e.g. public / held-out / commercial repositories, or a 50/50 public–private split—and treat public–private score divergence as a contamination signal, including leakage modes such as gold trajectories shipped in model distributions.[S3][S4] Open static GitHub-sourced suites can stop measuring frontier progress when models reproduce gold patches and remaining hard items have flawed tests, so gains track exposure and suite artifacts rather than capability.[S5] Weak harness isolation also defeats sealed-looking designs (gold answers shipped with tasks, agent/evaluator co-residence, unrotated public tests); rotating instances and private held-out scoring of submitted outputs are the prescribed control.[S6]

**Transfer — sealed held-in/held-out acceptance for harness changes.** Mechanism: freeze graders and population before mutation; accept only strict held-in gain and held-out non-regression (plus safety/regression suite). Signal: harness_validation_completed with the same population_id, non-negative counts, accepted only on that gate. Does not apply when live budget is zero—the deterministic host suite remains an offline control-plane floor, not multi-turn paid reliability proof.[S20]

### Outcome grading over process and “run finished”
Outcome grading must score final environment state (DB reservation, suite result), not transcript claims or a driver exiting zero.[S7] For coding agents, deterministic unit/integration graders (fail-to-pass without breaking pass-to-pass) are the primary independent reliability signal; tool-sequence checks are brittle because agents can solve validly via unanticipated paths.[S8]

**Transfer — task success = final-state grader pass.** Mechanism: code outcome/state checkers on environment or suite outputs. Signal: trial.success only when grader.pass; metrics null/reject without grader evidence. Does not apply as sole signal for open-ended subjective UX without human/model rubrics calibrated to humans.[S19]

### Grader metrics: pass@1, pass@k, pass^k
pass@k estimates P(≥1 correct in k independent trials) and rises with k; coding product settings often care most about pass@1 (first-try success).[S9] pass^k estimates P(all k succeed) and falls with k—the consistency metric when every interaction must work (e.g. SOTA tools agents under 50% task success and pass^8 under 25% on retail).[S10] At k=1 both equal the per-trial rate; as k grows they diverge (pass@k can approach 100% while pass^k falls toward 0%), so the product mode dictates which metric is honest.[S11]

**Transfer — report both on non-deterministic/live subsets.** Mechanism: k independent trials per task; pass@k = ≥1 success; pass^k = all k succeed. Signal: pass@1 and pass^3 (or similar) on a fixed live population with final-state graders only. Does not apply to pure deterministic host smokes (router-eval, check-freeze), where one run is enough and pass^k collapses to binary suite green.[S21]

### Adversarial claim verification and answer-quality floors
Independent reliability also needs mechanical quality floors that fail missing evidence (not a subjective 10/10), plus anti-gaming checks: weak tests hide wrong code (large pass@k cuts), and reward hacks or benchmark awareness inflate outcomes unless trajectories and bypass-resistant graders are inspected.[S12]

**Transfer — answer-quality as harness honesty floor, not agent quality.** Mechanism: deterministic helper + versioned fixtures (research/handoff/overclaim). Signal: answer-quality-check/eval pass on durable artifacts; explicit not-verified for model quality and user satisfaction. Does not substitute for final-state task graders or held-out outcome suites when claiming coding-agent reliability.[S24]

### Capability matrices: expiry and proof_command discipline
A single JSON SSOT can attach each runtime claim to label (confirmed|proxy_supported|blocked|unknown), verified_at, expires_after_days, proof_command, and proof_result, with re-label only from proof_command output—not prose.[S13] Expiry is mechanical: confirmed/proxy_supported rows past verified_at + expires_after_days fail CI-style smoke unless re-verified or relabelled.[S14] Date-only refresh is forbidden: on expiry, run proof_command or set unknown.[S15] Honesty signal vs theater: live multi-model/subagent claims stay unknown with explicit offline-not-possible proof_result rather than remaining confirmed; success is label moves unknown→confirmed|blocked with non-stale proof (optional live_agent_proof: ran|skipped).[S16] Executable proof_results (command exit 0 / smoke paths) beat docs-smoke string pins, which are weaker behavioral signal.[S17] Production agent-first harnesses similarly enforce knowledge freshness with linters/CI and recurring agents that open PRs when docs diverge from code—not manual date stamps alone.[S18]

**Transfer — matrices already partially shipped dual-runtime.** Mechanism: labels re-proved only by running proof_command, never date-only refresh. Signal: verified_at + proof_result tied to dual-runtime/check-freeze/router proofs; expired → re-prove or unknown. Does not apply to session-scoped host features that cannot be proved offline—they must stay unknown/blocked, not “confirmed” via docs.[S22]

### Rejected: multi-agent hops as quality
“More multi-agent hops ⇒ higher quality” fails without independent verification. Multi-agent systems can beat single-agent on breadth-first parallel research, but at ~15× tokens, with token usage explaining most variance on some evals—not hop count—and coding/shared-context domains are poor fits; complexity should be added only when outcomes improve. Local blind gates have rejected automatic full panels after repeated large latency multipliers without quality gain.[S23]

- "Question 2 uncertainty: No single primary source unifies all four design axes (final-state-only grading, pass@1/pass@k/pass^k, answer-quality floors, adversarial claim verification) into one coding-agent standard; synthesis is cross-source."
- "Question 2 uncertainty: Exact conditions under which LLM-as-judge taste/quality floors remain calibrated versus gaming for open-ended feature tasks (Senior SWE-Bench validation agent + taste judge) are still partly empirical and nondeterministic."
- "Question 2 uncertainty: How much sealed held-out surfaces reduce contamination/hacking for production coding-agent evals is stated as design practice (private task sets, sealed_held_out) but not quantified as a universal effect size here."
